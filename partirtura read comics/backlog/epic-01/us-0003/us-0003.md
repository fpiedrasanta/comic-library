# US-0003 — Recuperar contraseña

## Historia de usuario

**Como** usuario registrado de Comic Library  
**quiero** poder recuperar mi contraseña si la olvidé  
**para** volver a acceder a mi cuenta sin necesidad de contactar a soporte.

---

## Objetivo

Implementar el flujo completo de recuperación de contraseña mediante correo electrónico.

El usuario podrá solicitar la recuperación ingresando su email, recibir un código temporal de verificación y, si el código es válido, establecer una nueva contraseña.

El proceso debe mantener las reglas de seguridad existentes y no revelar información sobre la existencia de cuentas.

---

## Flujo funcional

El flujo completo será:

```text
Login
  │
  └── ¿Olvidaste tu contraseña?
          │
          ▼
   Formulario de recuperación
          │
          │ Ingresa email
          ▼
   POST /api/users/forgot-password
          │
          ▼
   Respuesta genérica
          │
          ▼
   Usuario recibe email
          │
          ▼
   Pantalla ingresar código
          │
          │ Código de 6 dígitos
          ▼
   Validación del código
          │
          ▼
   Formulario nueva contraseña
          │
          │ Nueva contraseña
          │ Confirmación
          ▼
   POST /api/users/reset-password
          │
          ▼
   Contraseña actualizada
          │
          ▼
       Login
```

---

# 1. Solicitar recuperación

El usuario podrá acceder al flujo desde la pantalla de Login mediante una opción:

```text
¿Olvidaste tu contraseña?
```

Al seleccionarla será dirigido a la pantalla de recuperación.

La pantalla solicitará:

```text
Email
```

El usuario enviará el formulario.

La API deberá generar y enviar un código de recuperación cuando corresponda.

---

# 2. No revelar si el email existe

Este punto es obligatorio.

El sistema **no debe permitir determinar si un email está registrado en Comic Library**.

Por lo tanto, ante una solicitud de recuperación:

### Email existente

```text
Usuario ingresa email
        ↓
Email existe
        ↓
Generar código
        ↓
Enviar email
        ↓
Responder correctamente
```

### Email inexistente

```text
Usuario ingresa email
        ↓
Email no existe
        ↓
NO generar código
        ↓
NO enviar email
        ↓
Responder exactamente igual que en el caso anterior
```

Desde el punto de vista del frontend, ambos casos deben ser indistinguibles.

No debe existir una respuesta como:

```text
"El usuario no existe."
```

ni:

```text
"El email no está registrado."
```

La respuesta debe utilizar un mensaje genérico.

Ejemplo:

```text
Si el email corresponde a una cuenta válida, recibirás un código para recuperar tu contraseña.
```

---

# 3. Código de recuperación

El sistema debe generar un código numérico de:

```text
6 dígitos
```

Ejemplo:

```text
126829
```

El código:

- debe ser generado de manera segura;
- debe tener una fecha de expiración;
- debe ser de un solo uso;
- no debe almacenarse en texto plano si la implementación de seguridad del proyecto establece almacenamiento mediante hash;
- debe invalidarse después de utilizarse correctamente.

La duración del código debe ser configurable.

No debe quedar hardcodeada en el código.

---

# 4. Email de recuperación

El usuario deberá recibir un email con el código de recuperación.

El correo debe indicar claramente:

```text
Tu código de recuperación
126829
```

El código debe visualizarse claramente separado del texto.

El correo debe indicar también que:

- el código es confidencial;
- tiene una duración limitada;
- no debe compartirse;
- si el usuario no solicitó el cambio, puede ignorar el mensaje.

El contenido del email deberá respetar el mecanismo existente de templates utilizado por Comic Library.

---

# 5. Ingreso del código

El usuario será dirigido a una pantalla para ingresar el código de 6 dígitos.

La interfaz deberá permitir:

- ingresar los 6 dígitos;
- pegar un código completo de 6 dígitos;
- mostrar visualmente los seis campos;
- avanzar correctamente entre campos;
- validar que solamente se ingresen números.

Si el usuario pega:

```text
126829
```

los seis campos deben completarse:

```text
[1][2][6][8][2][9]
```

No debe quedar solamente el primer dígito.

---

# 6. Temporizador

La pantalla de ingreso del código deberá mostrar el tiempo restante para utilizarlo.

El backend deberá proporcionar al frontend la información necesaria para determinar cuánto tiempo permanece vigente el código.

El frontend deberá mostrar un temporizador.

Ejemplo:

```text
El código vence en 00:59
```

El temporizador debe actualizarse hasta llegar a:

```text
00:00
```

Una vez expirado:

- el código no debe poder utilizarse;
- la interfaz debe informar que el código expiró;
- debe ofrecer la posibilidad de solicitar/reenviar un nuevo código, según el endpoint definido.

---

# 7. Reenvío del código

El usuario deberá poder solicitar nuevamente el código de recuperación.

El reenvío debe:

- generar un nuevo código;
- invalidar el código anterior;
- establecer una nueva expiración;
- enviar el nuevo código por email.

Debe respetarse cualquier regla de seguridad o limitación de frecuencia definida por el backend.

El frontend deberá utilizar la información devuelta por la API para reiniciar el temporizador.

---

# 8. Validación del código

El backend deberá validar:

- que el código corresponda al proceso de recuperación;
- que no haya expirado;
- que no haya sido utilizado previamente;
- que sea válido para el usuario correspondiente.

Si el código es incorrecto:

```text
Código inválido.
```

Si el código expiró:

```text
El código expiró.
```

Estas respuestas pueden diferenciarse porque en este punto el usuario ya está dentro del flujo de recuperación.

No obstante, no deben revelar información adicional sobre la existencia de la cuenta.

---

# 9. Nueva contraseña

Una vez validado correctamente el código, el usuario podrá ingresar:

```text
Nueva contraseña
Confirmar contraseña
```

La contraseña deberá cumplir las reglas de contraseña fuerte existentes:

- mínimo 8 caracteres;
- al menos un número;
- al menos una letra minúscula;
- al menos una letra mayúscula;
- al menos un carácter especial.

La interfaz debe mostrar visualmente el cumplimiento de cada regla.

Ejemplo:

```text
✓ Mínimo 8 caracteres
✓ Al menos un número
✗ Al menos una mayúscula
✓ Al menos una minúscula
✗ Al menos un carácter especial
```

Las reglas deberán visualizarse en verde cuando se cumplan y en rojo cuando no se cumplan.

---

# 10. Confirmación de contraseña

El usuario deberá ingresar la contraseña dos veces.

La interfaz debe verificar que:

```text
Nueva contraseña == Confirmar contraseña
```

Si no coinciden, debe informar claramente el error y no permitir continuar.

La validación debe existir tanto en frontend como en backend.

---

# 11. Actualización de contraseña

Una vez que:

- el código sea válido;
- el código no esté expirado;
- el código no haya sido utilizado;
- la nueva contraseña sea válida;
- ambas contraseñas coincidan;

la API deberá actualizar la contraseña del usuario.

La contraseña debe almacenarse utilizando el mecanismo de hashing de contraseñas existente.

Nunca debe almacenarse en texto plano.

---

# 12. Invalidación del proceso

Después de actualizar correctamente la contraseña:

- el código de recuperación debe quedar invalidado;
- no debe poder reutilizarse;
- cualquier estado temporal asociado al proceso debe quedar correctamente finalizado.

---

# 13. Sesiones existentes

Al cambiar la contraseña, se debe determinar el comportamiento de los Refresh Tokens existentes.

La decisión esperada para esta User Story es:

```text
Cambio exitoso de contraseña
        ↓
Invalidar Refresh Tokens existentes
        ↓
Usuario debe volver a autenticarse
```

Esto evita que una sesión previamente comprometida continúe siendo válida después de un cambio de contraseña.

El nuevo login generará nuevos tokens.

---

# 14. Seguridad

El flujo debe respetar las siguientes reglas:

- No revelar si un email existe.
- No devolver códigos de recuperación en las respuestas de la API.
- No almacenar códigos sensibles en texto plano cuando el diseño de seguridad del proyecto indique hashing.
- No almacenar contraseñas en texto plano.
- No registrar códigos ni contraseñas en logs.
- Los códigos deben expirar.
- Los códigos deben ser de un solo uso.
- Los códigos anteriores deben invalidarse al generar uno nuevo.
- Los Refresh Tokens existentes deben invalidarse después de un cambio exitoso de contraseña.
- No utilizar información sensible en mensajes de error.

---

# 15. Emails no validados

La recuperación de contraseña aplica únicamente a cuentas activas.

Un usuario cuyo email nunca fue validado no debe poder utilizar el flujo de recuperación de contraseña como mecanismo para activar la cuenta.

El comportamiento debe mantenerse coherente con las reglas existentes:

```text
Email no validado
    ↓
No es una cuenta activa
    ↓
No puede recuperar contraseña
```

La respuesta hacia el cliente debe continuar siendo genérica para no revelar información sobre la existencia de la cuenta.

---

# 16. Relación con Login

Después de completar correctamente el cambio de contraseña:

```text
Cambio de contraseña exitoso
        ↓
Redirect a Login
        ↓
Usuario ingresa nuevas credenciales
        ↓
POST /api/users/login
        ↓
Nuevo Access Token
        +
Nuevo Refresh Token
        ↓
Usuario autenticado
```

No se debe autenticar automáticamente al usuario como consecuencia del cambio de contraseña, salvo que una decisión posterior del proyecto modifique explícitamente este comportamiento.

---

# 17. Endpoints esperados

Los endpoints deberán definirse y documentarse antes de implementar el frontend.

Como mínimo se espera contar con operaciones equivalentes a:

```text
POST /api/users/forgot-password
POST /api/users/validate-password-reset-code
POST /api/users/reset-password
POST /api/users/resend-password-reset-code
```

Los nombres definitivos deberán respetar las convenciones existentes del proyecto.

Los contratos de request y response deberán documentarse en:

```text
project/endpoints.md
```

---

# 18. Configuración

Los valores relacionados con recuperación de contraseña deberán configurarse mediante `appsettings.json` y configuración por ambiente cuando corresponda.

Por ejemplo:

```text
PasswordReset:TokenExpirationMinutes
```

El nombre definitivo deberá respetar las convenciones existentes.

No deben existir valores hardcodeados para:

- duración del código;
- límites de reenvío;
- cualquier otro comportamiento configurable.

Estas configuraciones son configuración de aplicación y **no deben agregarse a `backend-stack-technology.md`**.

---

# 19. Frontend

El frontend deberá incorporar las pantallas necesarias para el flujo.

Como mínimo:

```text
Login
   ↓
Forgot Password
   ↓
Verify Code
   ↓
Change Password
```

La pantalla de Login ya existe y deberá incorporar el acceso al flujo.

La pantalla de Change Password ya forma parte de las interfaces diseñadas y deberá reutilizarse/adaptarse.

El diseño visual deberá respetar los templates y las reglas existentes del Public Web.

---

# 20. Criterios de aceptación

La User Story se considera completada cuando:

1. El usuario puede iniciar el proceso desde Login.
2. Puede ingresar su email.
3. La API no revela si el email existe.
4. Una cuenta válida recibe un código por email.
5. El código tiene exactamente 6 dígitos numéricos.
6. El código tiene expiración configurable.
7. El frontend muestra el tiempo restante.
8. El usuario puede reenviar el código.
9. El reenvío invalida el código anterior.
10. El usuario puede pegar los 6 dígitos y los seis campos se completan correctamente.
11. Un código inválido es rechazado.
12. Un código expirado es rechazado.
13. Un código utilizado previamente es rechazado.
14. Un código válido permite continuar al cambio de contraseña.
15. La nueva contraseña debe cumplir las reglas de contraseña fuerte.
16. La interfaz muestra visualmente el cumplimiento de cada regla.
17. Las contraseñas deben coincidir.
18. El backend valida nuevamente las reglas de contraseña.
19. La contraseña se almacena hasheada.
20. El código queda invalidado después de utilizarse.
21. Los Refresh Tokens existentes quedan invalidados después de cambiar la contraseña.
22. El usuario no queda autenticado automáticamente.
23. El usuario es dirigido nuevamente al Login.
24. Puede iniciar sesión utilizando su nueva contraseña.
25. Se genera un nuevo Access Token y Refresh Token mediante el flujo normal de Login.
26. No se exponen contraseñas, códigos ni Refresh Tokens en respuestas JSON.
27. No se registran contraseñas ni códigos en logs.
28. Las cuentas cuyo email no fue validado no pueden utilizar el flujo para activar una cuenta.
29. La configuración de expiración no queda hardcodeada.
30. Los contratos de los endpoints están documentados.
31. El comportamiento queda documentado en los documentos correspondientes.
32. `Application`, `Infrastructure` y `Api` compilan correctamente.
