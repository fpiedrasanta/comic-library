# US-0010 — Administrar usuarios

## Tipo

User Story funcional.

## Objetivo

Permitir a los administradores consultar y supervisar los usuarios registrados desde el Dashboard.

La funcionalidad debe permitir buscar, filtrar, ordenar, paginar y visualizar información de los usuarios, incluyendo su fotografía de perfil y la cantidad e historial de baneos.

La administración de usuarios definida en esta User Story es exclusivamente de consulta.

El administrador no puede modificar la identidad, información personal ni credenciales de otro usuario.

Las operaciones relacionadas con los baneos pertenecen a US-0012 — Administrar bloqueos/baneos de usuarios.

## Template

Ver template en: `\read comics\partirtura read comics\ux_ui\admin-users-dashboard.html`

## Acceso

Esta funcionalidad pertenece exclusivamente al Dashboard.

Solo los usuarios que posean permisos de administrador pueden acceder a la consulta de usuarios.

El backend debe validar los permisos del usuario autenticado.

El frontend no puede determinar ni asumir por sí mismo que un usuario posee permisos administrativos.

## Listado de usuarios

El Dashboard debe mostrar un listado paginado de usuarios.

Cada fila debe mostrar como mínimo:

| Dato | Función |
|---|---|
| Avatar | Fotografía de perfil del usuario. |
| Apellido y Nombre | Identificación. Ordenable por apellido. |
| Email | Identificación. Ordenable. |
| Estado | Activo / Inactivo. Ordenable. |
| Baneado | Sí / No. Indica si actualmente existe un ban vigente. Ordenable. |
| Cantidad de baneos | Cantidad total de baneos registrados para el usuario. Ordenable. |
| Fecha de registro | Fecha de registro. Ordenable. |

La columna de fecha de registro debe ser la primera columna de datos del listado y el ordenamiento inicial debe ser:

- `orderBy`: `CreatedAt`
- `orderDir`: `DESC`

De esta forma, los usuarios registrados más recientemente aparecen primero.

## Avatar

El avatar del usuario debe mostrarse directamente en la grilla.

El response del endpoint de listado debe incluir la información necesaria para que el Dashboard pueda renderizar el avatar sin realizar una consulta adicional por cada usuario.

El usuario puede no tener avatar.

En ese caso, el frontend debe utilizar el avatar o representación visual por defecto definida por el sistema.

El avatar mostrado en la grilla es exclusivamente de consulta.

El administrador no puede modificar, reemplazar ni eliminar el avatar desde esta funcionalidad.

## Visualización rápida del usuario

Cada fila debe incluir una acción de visualización representada mediante un ícono de "ojo".

Al seleccionar esta acción, el Dashboard debe mostrar un modal con formato de ficha o carnet de usuario.

El objetivo del modal es permitir una identificación rápida y visual del usuario.

El modal debe mostrar:

- Foto.
- Nombre.
- Apellido.
- Email.
- Nacionalidad.

La presentación debe priorizar la visualización clara de la fotografía y de los datos básicos de identificación.

La visualización de la fotografía permite al administrador realizar controles visuales y de moderación sobre el contenido del perfil.

El modal es exclusivamente de consulta.

No debe permitir:

- Modificar el nombre.
- Modificar el apellido.
- Modificar el email.
- Modificar la nacionalidad.
- Modificar la contraseña.
- Modificar o reemplazar el avatar.
- Eliminar el avatar.
- Eliminar la cuenta.

## Búsqueda

El listado debe disponer de un buscador genérico.

El criterio ingresado debe buscar coincidencias por:

- Apellido.
- Email.

La búsqueda no debe realizarse por nombre de pila.

El criterio `search` es opcional.

Si no se informa un criterio de búsqueda, deben considerarse todos los usuarios que cumplan con los demás filtros.

## Filtros

El listado debe permitir filtrar por estado de cuenta.

### Estado

Valores disponibles:

- Activo.
- Inactivo.

El filtro es opcional.

### Baneado

Valores disponibles:

- Sí.
- No.

El filtro es opcional.

El valor `Baneado = Sí` debe representar exclusivamente usuarios que tengan un ban vigente al momento de realizar la consulta.

Un usuario que haya tenido baneos anteriores pero cuyo último ban haya finalizado debe aparecer como:

- `Baneado = No`.

## Ordenamiento

El listado debe permitir ordenar por las columnas definidas como ordenables.

La consulta debe permitir indicar:

- Columna.
- Dirección.

Las direcciones permitidas son:

- `ASC`.
- `DESC`.

El backend debe utilizar un conjunto explícito de campos permitidos para el ordenamiento.

No debe utilizarse directamente un valor arbitrario recibido del frontend como expresión de ordenamiento sobre la base de datos.

El ordenamiento por defecto debe ser:

- Fecha de registro.
- Descendente.

## Paginación

El listado debe utilizar paginación del lado del servidor.

La consulta debe permitir indicar:

- `currentPage`.
- `pageSize`.

El backend debe devolver la información necesaria para construir el paginado en el Dashboard, incluyendo como mínimo:

- Registros de la página actual.
- Página actual.
- Tamaño de página.
- Cantidad total de registros.
- Cantidad total de páginas.

Los valores por defecto y los límites máximos de `pageSize` deben estar definidos por el backend.

## Consulta de usuarios

Conceptualmente, el Dashboard debe poder realizar una consulta con una estructura equivalente a:

{
   currentPage: 1,
   pageSize: 12,
   orderBy: "LastName",
   orderDir: "ASC",
   search: "Piedra",
   isBanned: true,
   isActive: true
}

Los siguientes criterios son opcionales:

- `search`.
- `isBanned`.
- `isActive`.
- `orderBy`.
- `orderDir`.

La paginación debe mantener los filtros y el ordenamiento seleccionados al cambiar de página.

## Response del listado

El response de cada usuario debe proporcionar la información necesaria para representar completamente una fila de la grilla.

Como mínimo debe incluir:

- Identificador del usuario.
- Avatar o referencia necesaria para renderizarlo.
- Nombre.
- Apellido.
- Email.
- Estado de la cuenta.
- Estado de baneo vigente.
- Cantidad total de baneos.
- Fecha de registro.

El backend debe resolver el estado de baneo vigente y la cantidad de baneos sin requerir consultas adicionales por cada usuario desde el frontend.

La consulta debe evitar el patrón N+1.

## Cantidad de baneos

La cantidad de baneos representa el total histórico de baneos asociados al usuario.

Debe incluir:

- Baneos vigentes.
- Baneos finalizados.
- Baneos anteriores.

Por ejemplo, un usuario puede tener:

- Cantidad de baneos: `3`
- Baneado actualmente: `No`

Esto significa que tuvo tres baneos históricos, pero ninguno se encuentra vigente actualmente.

El detalle y administración de los baneos pertenece a US-0012.

## Información del usuario

El administrador debe poder visualizar la información básica del usuario mediante el modal de detalle.

La información consultada debe corresponder exclusivamente al usuario seleccionado.

La consulta no otorga permisos para modificar la información.

## Restricciones de modificación

El administrador no puede modificar los datos personales o credenciales de otro usuario.

No puede:

- Cambiar nombre.
- Cambiar apellido.
- Cambiar email.
- Cambiar contraseña.
- Cambiar nacionalidad.
- Cambiar avatar.
- Eliminar avatar.
- Modificar credenciales.
- Eliminar físicamente al usuario.
- Reactivar una cuenta mediante la modificación de sus datos.
- Hacerse pasar por otro usuario.

El hecho de que un usuario tenga permisos de administrador no implica que pueda modificar la identidad o las credenciales de otros usuarios.

## Bajas de usuarios

La baja de una cuenta no forma parte de las operaciones de esta User Story.

La baja de la propia cuenta está definida en US-0009.

Las operaciones administrativas relacionadas con bloqueos y restricciones de acceso están definidas en US-0012.

## Seguridad

El acceso a la funcionalidad debe estar protegido tanto en el Dashboard como en el backend.

El backend debe verificar que el usuario autenticado posee permisos de administrador.

No debe confiar en un rol o permiso enviado por el frontend.

La API no debe exponer:

- Contraseñas.
- Hashes de contraseñas.
- Refresh Tokens.
- Códigos OTP.
- Tokens de recuperación.
- Otros secretos utilizados para autenticación.

La información devuelta debe limitarse a la necesaria para la administración y supervisión de usuarios.

## Reglas

- Solo los administradores pueden consultar usuarios desde el Dashboard.
- Los administradores pueden consultar cualquier usuario.
- Los administradores pueden buscar por apellido o email.
- Los administradores pueden filtrar por estado.
- Los administradores pueden filtrar por baneo vigente.
- Los administradores pueden ordenar el listado.
- Los administradores pueden paginar el listado.
- Los administradores pueden visualizar el avatar.
- Los administradores pueden visualizar el detalle básico del usuario.
- Los administradores pueden visualizar la cantidad histórica de baneos.
- Un administrador no puede modificar los datos personales de otro usuario.
- Un administrador no puede modificar las credenciales de otro usuario.
- Un administrador no puede cambiar la contraseña de otro usuario.
- Un administrador no puede modificar el email de otro usuario.
- Un administrador no puede modificar el avatar de otro usuario.
- Un administrador no puede eliminar otro usuario.
- Un administrador no puede utilizar esta funcionalidad para hacerse pasar por otro usuario.
- El estado `Baneado` representa únicamente la existencia de un ban vigente.
- La cantidad de baneos representa el historial total de baneos.
- La administración de los baneos pertenece a US-0012.

## Resultado esperado

Desde el Dashboard, un administrador debe poder consultar eficientemente los usuarios del sistema mediante un listado paginado.

Debe poder:

1. Buscar usuarios por apellido o email.
2. Filtrar usuarios por estado activo/inactivo.
3. Filtrar usuarios por estado de baneo vigente.
4. Ordenar los resultados.
5. Cambiar de página.
6. Visualizar el avatar de cada usuario directamente en la grilla.
7. Visualizar la cantidad histórica de baneos.
8. Identificar rápidamente si un usuario está actualmente baneado.
9. Abrir una ficha tipo carnet mediante el ícono de visualización.
10. Consultar en esa ficha la foto, nombre, apellido, email y nacionalidad.

Toda la funcionalidad debe ser de consulta y supervisión, sin permitir al administrador modificar la identidad ni las credenciales de los usuarios.
