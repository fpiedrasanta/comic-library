# US-0004 — Autenticación mediante Google

## User Story

**Como** usuario de Comic Library,  
**quiero** poder registrarme e iniciar sesión utilizando mi cuenta de Google,  
**para** acceder a la aplicación sin tener que utilizar necesariamente email y contraseña.

---

## Objetivo

Incorporar autenticación mediante Google al sistema de usuarios existente.

La autenticación mediante Google debe integrarse con el modelo de usuario actual y utilizar el mismo mecanismo de sesión que el Login tradicional:

- Access Token.
- Refresh Token.
- Refresh Token transportado mediante cookie `HttpOnly`.

No se debe crear un usuario diferente cuando un usuario existente utiliza Google con el mismo email.

---

# Reglas funcionales

## 1. Usuario registrado normalmente → Login con Google

Si un usuario se registró previamente mediante:

```text
Email + Password
```

y posteriormente utiliza:

```text
Continuar con Google
```

utilizando una cuenta de Google cuyo email coincide con el email registrado en Comic Library:

```text
User existente
        +
Google con mismo email
        ↓
Autenticación exitosa
        ↓
Generar sesión
```

No se debe crear un segundo usuario.

El usuario existente debe continuar siendo el mismo `User`.

---

## 2. Usuario registrado normalmente → Login tradicional

Debe continuar funcionando exactamente como hasta ahora:

```text
Email + Password
        ↓
Login
        ↓
Access Token + Refresh Token
```

La incorporación de Google no debe modificar el comportamiento existente del Login tradicional.

---

## 3. Usuario registrado mediante Google → Registro normal

Si un usuario fue creado originalmente utilizando Google y posteriormente intenta registrarse mediante el formulario tradicional utilizando el mismo email:

```text
Usuario existente
        ↓
Intento de registro con mismo email
        ↓
"El usuario ya existe."
```

Debe aplicarse la misma regla de existencia de usuario que actualmente utiliza el registro.

No debe crearse un segundo `User`.

---

## 4. Usuario registrado mediante Google → Login con email y password

Si un usuario fue creado originalmente mediante Google y todavía no tiene una contraseña configurada:

```text
Google User
    ↓
Login Email + Password
    ↓
Credenciales inválidas
```

La API debe devolver el mismo comportamiento genérico utilizado actualmente para credenciales incorrectas.

No debe devolver mensajes como:

```text
"Debe ingresar con Google."
```

ni:

```text
"El usuario está registrado con Google."
```

ni:

```text
"Este email está asociado a una cuenta de Google."
```

### Motivo

No se debe revelar información adicional que permita determinar:

- si el email existe;
- cómo fue creado el usuario;
- qué proveedor de autenticación utiliza.

El comportamiento debe ser consistente con las reglas de seguridad del Login existente.

---

## 5. Usuario registrado mediante Google → Recuperar contraseña

Un usuario creado originalmente mediante Google debe poder utilizar:

```text
Recuperar contraseña
```

para establecer una contraseña.

Flujo:

```text
Usuario Google
      ↓
Recuperar contraseña
      ↓
Establecer nueva contraseña
      ↓
Password configurada
      ↓
Puede utilizar:
   ├── Google
   └── Email + Password
```

Una vez establecida la contraseña, el usuario puede autenticarse mediante cualquiera de los dos mecanismos.

No debe ser necesario crear un nuevo usuario.

---

# Datos obtenidos desde Google

Google debe proporcionar como mínimo los datos necesarios para identificar y crear el usuario:

- Email.
- Nombre.
- Apellido.
- Avatar, si está disponible.

Estos datos deben utilizarse para completar las propiedades correspondientes de `User`.

No almacenar información adicional de Google sin una necesidad funcional concreta.

---

# GoogleData

No crear inicialmente una propiedad o estructura `GoogleData` solamente para almacenar la respuesta completa de Google.

Si los datos necesarios para Comic Library ya están representados en `User`, deben almacenarse directamente en `User`.

Solamente incorporar `GoogleData` si durante la implementación aparece una necesidad concreta de conservar información de Google que no pueda representarse adecuadamente en el modelo actual.

---

# ExternalIdentity

No incorporar inicialmente una entidad `ExternalIdentity`.

Para el alcance actual, la identificación mediante Google se resolverá utilizando el email del usuario.

No implementar una abstracción genérica para múltiples proveedores de identidad salvo que exista una necesidad funcional concreta.

La solución debe mantenerse simple y acorde con la arquitectura actual.

---

# Creación de usuario mediante Google

Cuando Google autentique correctamente a un usuario:

### Usuario existente

Si existe un `User` con el mismo email:

```text
Google authentication
        ↓
Buscar User por email
        ↓
User encontrado
        ↓
Autenticar usuario existente
```

No crear un nuevo usuario.

### Usuario inexistente

Si no existe un `User` con ese email:

```text
Google authentication
        ↓
Buscar User por email
        ↓
No encontrado
        ↓
Crear User
        ↓
Autenticar usuario
```

Los datos obtenidos de Google deben utilizarse para completar el nuevo usuario.

---

# Email validado

Un usuario creado mediante Google debe considerarse con su identidad de email validada como resultado de la autenticación proporcionada por Google.

No debe requerirse que el usuario vuelva a completar el flujo de validación de email utilizado para el registro tradicional.

---

# Sesión

El resultado exitoso del Login mediante Google debe utilizar exactamente el mismo mecanismo de autenticación que el Login tradicional.

Debe generarse:

```text
Access Token
```

y:

```text
Refresh Token
```

El Refresh Token debe transportarse mediante la cookie `HttpOnly` existente.

No crear un mecanismo de sesión diferente para Google.

El frontend debe recibir el mismo tipo de respuesta pública que recibe el Login tradicional.

---

# Seguridad

La implementación debe respetar las reglas de seguridad existentes.

Especialmente:

- No revelar si un email existe.
- No revelar mediante mensajes de error qué proveedor utilizó el usuario.
- No generar usuarios duplicados.
- No almacenar tokens de Google innecesariamente.
- No almacenar credenciales de Google.
- No registrar información sensible de Google en logs.
- No devolver información sensible al frontend.
- Mantener el Refresh Token exclusivamente mediante cookie `HttpOnly`.
- Mantener la generación del Access Token mediante el mecanismo JWT existente.

---

# Arquitectura

La incorporación de Google debe respetar la arquitectura actual:

```text
Presentation
      ↓
Application
      ↓
Infrastructure
      ↓
Domain
```

La lógica de negocio debe permanecer en Application.

La integración técnica con Google debe implementarse como capacidad de Infrastructure detrás de una interfaz definida en Application cuando corresponda.

Presentation debe encargarse exclusivamente de HTTP, requests, responses, cookies y detalles propios del protocolo utilizado.

No introducir lógica de negocio en Controllers.

---

# Reutilización

La funcionalidad de Google Login debe reutilizar los mecanismos existentes para:

- generación de JWT;
- generación de Refresh Token;
- cookies `HttpOnly`;
- manejo de usuarios;
- Unit of Work;
- manejo de errores;
- respuestas de API;
- configuración por ambiente.

No duplicar mecanismos existentes.

---

# Configuración

Toda configuración necesaria para Google debe ser configurable por ambiente.

Por ejemplo:

```text
Google:
    ClientId
    ClientSecret
```

Los valores reales no deben almacenarse directamente en código fuente.

La configuración debe incorporarse en los archivos de configuración correspondientes y/o mecanismos seguros de configuración utilizados por el proyecto.

No documentar valores concretos de credenciales.

Si se incorpora una nueva dependencia tecnológica para Google, actualizar:

```text
backend-stack-technology.md
```

Si solamente se incorporan valores de configuración, no documentarlos como una tecnología o dependencia.

---

# Criterios de aceptación

La User Story se considera cumplida cuando:

1. El usuario puede iniciar autenticación mediante Google.
2. Un usuario existente con el mismo email no genera un segundo `User`.
3. Un usuario registrado normalmente puede posteriormente utilizar Google Login con el mismo email.
4. Un usuario creado mediante Google no puede registrarse nuevamente con el mismo email.
5. Un usuario Google sin password que intenta Login tradicional recibe el mismo error genérico de credenciales inválidas.
6. No se revela que un usuario está registrado mediante Google.
7. Un usuario Google puede utilizar Recuperar contraseña.
8. Después de establecer una contraseña, el usuario puede autenticarse mediante Google o email/password.
9. Los datos necesarios obtenidos de Google se almacenan en las propiedades existentes de `User`.
10. No se crea `ExternalIdentity` sin una necesidad funcional concreta.
11. No se almacena `GoogleData` innecesariamente.
12. No se almacenan credenciales de Google.
13. El Login mediante Google genera el mismo Access Token utilizado por el Login tradicional.
14. El Refresh Token se establece mediante la cookie `HttpOnly` existente.
15. No se crea un mecanismo de sesión diferente para Google.
16. No se revelan datos sensibles mediante errores.
17. No se crean usuarios duplicados.
18. La integración respeta la arquitectura definida para el backend.
19. La configuración de Google puede variar por ambiente.
20. No existen credenciales hardcodeadas.
21. Se reutilizan los servicios existentes de JWT, Refresh Token, usuarios y manejo de sesión.
22. La aplicación compila correctamente.

# Fuera de alcance

Esta User Story no contempla:

- Login con Apple.
- Login con Microsoft.
- Login con otros proveedores.
- Entidad genérica `ExternalIdentity`.
- Administración de múltiples proveedores por usuario.
- Gestión avanzada de cuentas vinculadas.
- Desvinculación de Google.
- Eliminación de una cuenta Google vinculada.
- Sincronización permanente de datos del perfil de Google.
- Almacenamiento completo de la respuesta de Google.
