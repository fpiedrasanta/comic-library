# US-0006 — Autenticación y acceso al Dashboard administrativo

## Historia de usuario

**Como** administrador de Comic Library

**Quiero** poder autenticarme en el Dashboard administrativo mediante email y contraseña

**Para** acceder de forma segura a las funcionalidades de administración de la plataforma.

## Objetivo

Implementar la autenticación y autorización necesaria para acceder al Dashboard administrativo de Comic Library.

El Dashboard administrativo es una aplicación frontend independiente del Public Web, pero utiliza el mismo backend y sistema de identidad.

El acceso al Dashboard debe estar restringido exclusivamente a usuarios que posean un rol administrativo.

La autenticación administrativa debe utilizar el mecanismo de sesión existente del backend:

* Access Token JWT.
* Refresh Token.
* Refresh Token mediante cookie `HttpOnly`.
* Refresh Token Rotation.

No debe existir un mecanismo de autenticación separado únicamente por tratarse del Dashboard.

---

# 1. Aplicación Dashboard

El Dashboard administrativo constituye un frontend independiente del Public Web.

La arquitectura conceptual es:

```text
Public Web
    │
    └──────┐
           │
           ▼
       Backend API
           ▲
           │
    ┌──────┘
    │
Dashboard
```

Ambos frontends utilizan el mismo backend y el mismo sistema de identidad.

El Dashboard debe disponer de su propia pantalla de Login.

---

# 2. Métodos de autenticación

El Dashboard administrativo utilizará exclusivamente:

```text
Email + Password
```

No forman parte del acceso administrativo:

* Registro de usuarios.
* Login mediante Google.
* Otros proveedores de identidad.

Un usuario no debe poder crear por sí mismo una cuenta administrativa desde el Dashboard.

La autenticación mediante Google existente para el Public Web no debe habilitar automáticamente el acceso administrativo.

---

# 3. Login del Dashboard

El Dashboard debe proporcionar una pantalla de autenticación que permita ingresar:

```text
Email
Password
```

El flujo será:

```text
Dashboard
   │
   ▼
Login
   │
   ├── Email
   └── Password
   │
   ▼
Backend
   │
   ├── Validar credenciales
   ├── Verificar usuario
   ├── Verificar email validado
   └── Verificar rol administrativo
   │
   ▼
Generar sesión
   │
   ├── Access Token
   └── Refresh Token
   │
   ▼
Dashboard autenticado
```

El Login debe reutilizar los mecanismos existentes de autenticación y generación de tokens.

No deben implementarse mecanismos paralelos de generación de JWT o Refresh Tokens exclusivamente para el Dashboard.

---

# 4. Autorización administrativa

La autenticación y la autorización son responsabilidades diferentes.

Un usuario puede estar autenticado en Comic Library y aun así no tener autorización para utilizar el Dashboard.

El backend debe verificar que el usuario autenticado posea el rol administrativo requerido.

La regla inicial será:

```text
User
  │
  └── Role: Administrator
```

Solamente un usuario con el rol `Administrator` podrá acceder a los recursos administrativos.

La autorización debe ser realizada por el backend y no únicamente por el frontend.

Ocultar una pantalla o ruta del Dashboard no constituye un mecanismo de seguridad suficiente.

---

# 5. Rol Administrator

El sistema debe incorporar el concepto de rol de usuario necesario para identificar a los administradores.

Para la primera versión se utilizará un modelo simple de roles.

El rol inicial requerido será:

```text
Administrator
```

No se implementará inicialmente un sistema complejo de permisos, permisos por recurso o RBAC avanzado.

La arquitectura debe permitir evolucionar posteriormente hacia permisos más específicos si el producto lo requiere.

El rol administrativo no debe determinarse mediante:

* El email del usuario.
* Una lista hardcodeada de emails.
* Una condición específica dentro de un Controller.
* Una configuración del frontend.

La autorización debe basarse en la información de identidad/rol del usuario.

---

# 6. Usuario administrador inicial

La aplicación debe disponer de un usuario administrador inicial para permitir la puesta en funcionamiento del Dashboard.

Durante la inicialización del sistema debe garantizarse la existencia de un usuario administrador con:

```text
Email:
fede.piedrasanta@gmail.com
```

El usuario debe poseer el rol:

```text
Administrator
```

La contraseña inicial debe almacenarse utilizando el mecanismo de hashing de contraseñas existente.

Nunca debe almacenarse la contraseña en texto plano.

El sistema debe utilizar un mecanismo de inicialización/seed de datos apropiado para garantizar la existencia del usuario administrador inicial.

La inicialización debe ser idempotente:

```text
Primera ejecución
    ↓
Crear usuario administrador

Ejecuciones posteriores
    ↓
Usuario ya existe
    ↓
No duplicar usuario
```

No debe crearse un nuevo usuario administrador cada vez que se inicia la aplicación.

El valor concreto de la contraseña inicial no debe quedar documentado como texto plano en el código fuente ni en documentación funcional.

---

# 7. Recuperación de contraseña

El Dashboard debe permitir recuperar la contraseña mediante el mecanismo de recuperación existente en Comic Library.

El flujo será equivalente al existente:

```text
Dashboard Login
      │
      ▼
¿Olvidaste tu contraseña?
      │
      ▼
Recuperación mediante email
      │
      ▼
Código temporal
      │
      ▼
Nueva contraseña
      │
      ▼
Login
```

No debe implementarse un mecanismo de recuperación diferente exclusivamente para administradores.

Debe reutilizarse la infraestructura existente de:

* Generación de códigos.
* Expiración.
* Envío de emails.
* Validación.
* Hashing de contraseñas.
* Invalidación de Refresh Tokens.

La recuperación de contraseña no debe permitir convertir un usuario común en administrador.

El rol del usuario debe permanecer sin modificaciones como consecuencia del proceso de recuperación.

---

# 8. Usuario sin rol administrativo

Un usuario autenticado que no posea el rol `Administrator` no debe poder acceder a los recursos protegidos del Dashboard.

Si intenta acceder directamente a un endpoint administrativo:

```text
User autenticado
      ↓
Endpoint administrativo
      ↓
No posee Administrator
      ↓
Acceso rechazado
```

El frontend puede redirigir al usuario a una pantalla apropiada, pero la protección efectiva debe encontrarse en el backend.

La API no debe confiar en información enviada por el frontend para determinar si el usuario es administrador.

---

# 9. Usuario administrador autenticado

Cuando un usuario con rol `Administrator` inicia sesión correctamente:

1. El backend valida las credenciales.
2. Verifica que el email esté validado.
3. Verifica que el usuario posea el rol administrativo.
4. Genera un Access Token JWT.
5. Genera un Refresh Token.
6. Establece el Refresh Token mediante la cookie `HttpOnly` existente.
7. El Dashboard establece la sesión.
8. El administrador puede acceder a los recursos administrativos.

El Access Token debe utilizar el mecanismo JWT existente.

El Refresh Token debe continuar utilizando Refresh Token Rotation.

---

# 10. Renovación de sesión

El Dashboard debe poder renovar la sesión utilizando el mecanismo existente de Refresh Token.

Cuando expire el Access Token:

```text
Access Token expirado
       ↓
Refresh Token válido
       ↓
Nuevo Access Token
       +
Nuevo Refresh Token
       ↓
Continuar sesión
```

No debe solicitar nuevamente email y contraseña mientras el Refresh Token continúe siendo válido.

Debe mantenerse la política de Refresh Token Rotation existente.

---

# 11. Cierre de sesión

El Dashboard debe permitir cerrar la sesión del administrador.

El cierre de sesión debe utilizar el mecanismo de logout existente.

La sesión administrativa no debe permanecer activa indefinidamente después de que el usuario solicite cerrar sesión.

No debe crearse un mecanismo de logout diferente exclusivamente para el Dashboard.

---

# 12. Seguridad

La implementación debe respetar las reglas de seguridad existentes.

Especialmente:

* No almacenar contraseñas en texto plano.
* No almacenar Refresh Tokens en texto plano cuando el diseño existente utilice hashing.
* No exponer Refresh Tokens en respuestas JSON.
* Mantener el Refresh Token mediante cookie `HttpOnly`.
* No revelar información sensible mediante errores.
* No permitir acceso administrativo únicamente mediante controles del frontend.
* No utilizar emails hardcodeados como mecanismo de autorización.
* No permitir que un usuario común obtenga privilegios administrativos modificando requests.
* No registrar contraseñas, tokens ni códigos de recuperación en logs.
* Mantener la generación de JWT centralizada.
* Mantener la generación de Refresh Tokens centralizada.
* Mantener el manejo global de errores existente.

---

# 13. Diferencia entre Public Web y Dashboard

El mismo usuario puede autenticarse mediante el Public Web y posteriormente utilizar el Dashboard únicamente si posee el rol administrativo.

La existencia de dos aplicaciones frontend no implica la existencia de dos sistemas de identidad.

Conceptualmente:

```text
                    Backend API
                       │
             ┌─────────┴─────────┐
             │                   │
         Public Web           Dashboard
             │                   │
       Usuario normal       Administrator
```

El backend debe ser la autoridad final para determinar qué recursos puede utilizar cada usuario.

---

# 14. Registro

El Dashboard no debe proporcionar una funcionalidad de registro.

No debe existir:

```text
Register
Create account
Sign up
```

como mecanismo para obtener acceso al Dashboard.

Los usuarios administrativos deben ser creados mediante los mecanismos administrativos/de inicialización definidos por el sistema.

La administración de usuarios será abordada por la User Story correspondiente.

---

# 15. Google

El Dashboard no debe ofrecer:

```text
Continue with Google
```

La autenticación mediante Google existente pertenece al acceso del Public Web.

Un usuario que fue creado mediante Google puede tener posteriormente una contraseña mediante el flujo de recuperación existente, pero esto no implica que tenga acceso administrativo.

Para acceder al Dashboard debe cumplir igualmente la condición de poseer el rol `Administrator`.

---

# 16. Contratos API

Los endpoints necesarios para autenticación administrativa deben reutilizar los endpoints de autenticación existentes cuando sea posible.

No crear endpoints duplicados como:

```text
/api/admin/login
/api/admin/refresh
```

si los endpoints actuales pueden resolver correctamente la autenticación.

La autorización administrativa debe aplicarse sobre los endpoints administrativos mediante el mecanismo de autorización existente.

Si durante la implementación fuera necesario modificar los contratos actuales de autenticación para incorporar información de roles, los cambios deberán documentarse en:

```text
project/endpoints.md
```

---

# 17. Frontend Dashboard

El Dashboard debe incorporar como mínimo:

```text
Login
  │
  ├── Email
  ├── Password
  └── Recuperar contraseña
```

Una vez autenticado correctamente:

```text
Dashboard
```

El Dashboard debe impedir visualmente el acceso a funcionalidades administrativas cuando el usuario no esté autenticado.

Sin embargo, esta protección visual no reemplaza la autorización del backend.

El diseño visual debe respetar los prototipos y reglas correspondientes al Dashboard.

---

# 18. Criterios de aceptación

### CA-01 — Login administrativo exitoso

**Dado** un usuario existente con email validado

**Y** con rol `Administrator`

**Y** una contraseña correcta

**Cuando** inicia sesión desde el Dashboard

**Entonces** la API debe autenticarlo correctamente

**Y** debe generar un Access Token

**Y** debe establecer un Refresh Token mediante la cookie `HttpOnly`.

### CA-02 — Usuario sin rol administrativo

**Dado** un usuario autenticado

**Y** que no posee el rol `Administrator`

**Cuando** intenta acceder a un recurso administrativo

**Entonces** la API debe rechazar el acceso.

### CA-03 — Autorización en backend

**Dado** un usuario sin autorización administrativa

**Cuando** modifica manualmente una solicitud para acceder a un endpoint administrativo

**Entonces** el backend debe rechazar la solicitud.

### CA-04 — Login con credenciales incorrectas

**Dado** un usuario administrador

**Cuando** proporciona una contraseña incorrecta

**Entonces** la API debe rechazar la autenticación utilizando el comportamiento genérico existente.

### CA-05 — Email no validado

**Dado** un usuario cuyo email no fue validado

**Cuando** intenta iniciar sesión

**Entonces** no debe obtener una sesión autenticada.

### CA-06 — Google no disponible en Dashboard

**Dado** que el usuario accede al Login del Dashboard

**Entonces** no debe existir una opción de autenticación mediante Google.

### CA-07 — Registro no disponible

**Dado** que el usuario accede al Login del Dashboard

**Entonces** no debe existir una opción para registrarse.

### CA-08 — Recuperación de contraseña

**Dado** un usuario que olvidó su contraseña

**Cuando** utiliza la recuperación de contraseña desde el Dashboard

**Entonces** debe poder utilizar el flujo existente de recuperación mediante email.

### CA-09 — Recuperación no otorga privilegios

**Dado** un usuario sin rol `Administrator`

**Cuando** recupera correctamente su contraseña

**Entonces** debe conservar sus roles existentes

**Y** no debe obtener privilegios administrativos.

### CA-10 — Usuario administrador inicial

**Dado** una instalación nueva del sistema

**Cuando** se ejecuta la inicialización de datos

**Entonces** debe existir el usuario administrador inicial configurado

**Y** debe poseer el rol `Administrator`.

### CA-11 — Seed idempotente

**Dado** que el usuario administrador inicial ya existe

**Cuando** la aplicación vuelve a inicializar sus datos

**Entonces** no debe crear un usuario duplicado.

### CA-12 — Contraseña inicial

**Dado** el usuario administrador inicial

**Entonces** su contraseña debe encontrarse almacenada utilizando el mecanismo de hashing existente

**Y** nunca debe almacenarse en texto plano.

### CA-13 — Renovación de sesión

**Dado** un administrador autenticado

**Cuando** expira su Access Token

**Y** el Refresh Token continúa siendo válido

**Entonces** debe poder renovar la sesión utilizando el mecanismo existente.

### CA-14 — Refresh Token Rotation

**Dado** un Refresh Token administrativo válido

**Cuando** se utiliza para renovar la sesión

**Entonces** el Refresh Token anterior debe quedar invalidado

**Y** debe generarse uno nuevo.

### CA-15 — Logout

**Dado** un administrador autenticado

**Cuando** cierra sesión

**Entonces** debe finalizarse su sesión utilizando el mecanismo existente.

### CA-16 — Mismo usuario

**Dado** un usuario que posee acceso al Public Web y además tiene rol `Administrator`

**Cuando** accede al Dashboard

**Entonces** debe utilizar la misma identidad `User`

**Y** no debe crearse un usuario administrativo separado.

### CA-17 — Compilación

La solución debe compilar correctamente en:

```text
Application
Infrastructure
Api
```

y el Dashboard debe compilar correctamente según su stack tecnológico.

Esta User Story no incluye:

* Registro desde el Dashboard.
* Login mediante Google en el Dashboard.
* Login mediante otros proveedores.
* Gestión de usuarios.
* Edición de usuarios.
* Eliminación de usuarios.
* Activación/desactivación de usuarios.
* Gestión avanzada de roles.
* Gestión de permisos granulares.
* Gestión de contenido del catálogo.
* Gestión de editoriales.
* Gestión de franquicias.
* Gestión de series.
* Gestión de números.
* Gestión de listas.
* Estadísticas administrativas.
* Administración de países.
* Administración de personas relacionadas con cómics.

La gestión de usuarios será desarrollada en la User Story siguiente.

# Resultado esperado

Al finalizar esta User Story:

1. El Dashboard dispondrá de una pantalla de Login.
2. El Dashboard permitirá autenticarse únicamente mediante email y contraseña.
3. No existirá registro desde el Dashboard.
4. No existirá Login mediante Google desde el Dashboard.
5. Existirá recuperación de contraseña mediante el mecanismo existente.
6. Existirá un usuario administrador inicial.
7. El usuario administrador inicial tendrá el rol `Administrator`.
8. El seed del administrador será idempotente.
9. El administrador podrá iniciar sesión utilizando el mismo mecanismo de autenticación del sistema.
10. El Refresh Token continuará protegido mediante cookie `HttpOnly`.
11. La renovación continuará utilizando Refresh Token Rotation.
12. Los usuarios sin rol administrativo no podrán acceder a recursos del Dashboard.
13. La autorización administrativa será aplicada por el backend.
14. El Dashboard utilizará la misma identidad `User` que el Public Web.
15. No se creará un sistema de identidad paralelo para administradores.
16. La siguiente User Story podrá implementar sobre esta base la gestión administrativa de usuarios.
