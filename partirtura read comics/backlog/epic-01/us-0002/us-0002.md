# US-0002 — Iniciar sesión

## Historia de usuario

**Como** usuario registrado de Comic Library  
**Quiero** iniciar sesión utilizando mi email y contraseña  
**Para** acceder a la aplicación y mantener mi sesión activa sin tener que volver a ingresar mis credenciales cada vez que expire el token de acceso.

## Descripción

El usuario debe poder autenticarse utilizando las credenciales utilizadas durante el registro.

Cuando las credenciales sean correctas y el email del usuario haya sido validado, el sistema debe generar un Access Token (JWT) y un Refresh Token.

El Access Token será utilizado para acceder a los recursos protegidos de la aplicación.

Cuando el Access Token expire, el frontend podrá utilizar el Refresh Token para solicitar un nuevo Access Token sin requerir que el usuario vuelva a ingresar sus credenciales.

## Flujo principal

1. El usuario accede a la pantalla de login.
2. Ingresa su email.
3. Ingresa su contraseña.
4. Envía el formulario.
5. La API valida las credenciales.
6. La API verifica que el email del usuario haya sido validado.
7. La API genera un Access Token (JWT).
8. La API genera un Refresh Token.
9. La API devuelve ambos tokens al frontend.
10. El frontend establece la sesión del usuario.
11. El usuario puede acceder a las funcionalidades protegidas de Comic Library.

## Renovación de sesión

Cuando el Access Token haya expirado, el frontend debe poder utilizar el Refresh Token para solicitar un nuevo Access Token.

El usuario no debe tener que ingresar nuevamente su email y contraseña mientras el Refresh Token continúe siendo válido.

El proceso de renovación debe:

1. Recibir el Refresh Token.
2. Validar que el Refresh Token exista y sea válido.
3. Verificar que no haya sido revocado.
4. Verificar que no haya expirado.
5. Generar un nuevo Access Token.
6. Generar un nuevo Refresh Token.
7. Invalidar el Refresh Token anterior.
8. Devolver los nuevos tokens al frontend.

Se debe utilizar Refresh Token Rotation.

## Access Token

El Access Token debe:

- Ser un JWT.
- Respetar `Issuer` configurado.
- Respetar `Audience` configurado.
- Utilizar el `SecretKey` configurado.
- Respetar `ExpirationMinutes` configurado.
- Contener los claims necesarios para identificar al usuario autenticado.

## Refresh Token

El Refresh Token:

- No debe ser un JWT.
- Debe ser generado utilizando un mecanismo criptográficamente seguro.
- Debe tener una duración superior al Access Token.
- Debe estar asociado al usuario.
- Debe poder ser revocado.
- Debe tener una fecha de expiración.
- Debe ser invalidado cuando sea utilizado para obtener un nuevo Refresh Token.
- No debe almacenarse en texto plano si puede evitarse; preferentemente debe almacenarse utilizando un hash.

## Reglas de negocio

### Usuario inexistente

Si el email ingresado no corresponde a un usuario existente, la API debe devolver un error genérico de credenciales inválidas.

No debe informar que el email no existe.

### Contraseña incorrecta

Si el email existe pero la contraseña es incorrecta, la API debe devolver el mismo error genérico de credenciales inválidas.

No debe revelar que el email existe.

### Email no validado

Un usuario cuyo email no haya sido validado no puede iniciar sesión.

Si el registro pendiente ya no es válido según las reglas establecidas para usuarios no validados, debe ser tratado como un usuario inexistente.

### Usuario validado

Solamente un usuario cuyo email haya sido validado puede iniciar sesión.

### Access Token expirado

La expiración del Access Token no debe obligar al usuario a ingresar nuevamente sus credenciales si posee un Refresh Token válido.

### Refresh Token inválido

Si el Refresh Token:

- No existe.
- No corresponde al usuario.
- Fue revocado.
- Está expirado.
- Ya fue utilizado.

La API debe rechazar la solicitud de renovación y el frontend deberá solicitar nuevamente las credenciales del usuario.

## Seguridad

El sistema no debe revelar información que permita determinar si un email está registrado.

Los errores relacionados con email inexistente y contraseña incorrecta deben utilizar el mismo comportamiento y mensaje.

Los Refresh Tokens deben ser protegidos y nunca deben incluir información sensible del usuario.

## Criterios de aceptación

### CA-01 — Login exitoso

**Dado** un usuario existente con email validado  
**Y** una contraseña correcta  
**Cuando** el usuario inicia sesión  
**Entonces** la API debe devolver un Access Token y un Refresh Token válidos.

### CA-02 — Email inexistente

**Dado** un email que no corresponde a un usuario  
**Cuando** intenta iniciar sesión  
**Entonces** la API debe devolver un error genérico de credenciales inválidas.

### CA-03 — Contraseña incorrecta

**Dado** un usuario existente  
**Cuando** ingresa una contraseña incorrecta  
**Entonces** la API debe devolver el mismo error genérico de credenciales inválidas.

### CA-04 — Email no validado

**Dado** un usuario cuyo email no fue validado  
**Cuando** intenta iniciar sesión  
**Entonces** no debe obtener tokens de autenticación.

### CA-05 — Renovación del Access Token

**Dado** un Refresh Token válido  
**Cuando** el Access Token haya expirado  
**Y** el usuario solicite renovar su sesión  
**Entonces** la API debe devolver un nuevo Access Token y un nuevo Refresh Token.

### CA-06 — Refresh Token Rotation

**Dado** un Refresh Token válido  
**Cuando** sea utilizado para renovar la sesión  
**Entonces** el Refresh Token utilizado debe quedar invalidado  
**Y** la API debe generar un nuevo Refresh Token.

### CA-07 — Refresh Token expirado

**Dado** un Refresh Token expirado  
**Cuando** se solicita renovar la sesión  
**Entonces** la API debe rechazar la solicitud.

### CA-08 — Refresh Token revocado

**Dado** un Refresh Token revocado  
**Cuando** se solicita renovar la sesión  
**Entonces** la API debe rechazar la solicitud.

## Fuera de alcance

Esta User Story no incluye:

- Inicio de sesión con Google.
- Registro mediante Google.
- Recuperación de contraseña.
- Cambio de contraseña.
- Edición del perfil.
- Gestión de permisos o roles avanzados.
- Diseño visual definitivo de la aplicación.

Estas funcionalidades serán tratadas en User Stories independientes.

## Resultado esperado

Al finalizar esta User Story, un usuario registrado y con email validado podrá:

1. Iniciar sesión con email y contraseña.
2. Obtener un Access Token y un Refresh Token.
3. Utilizar el Access Token para acceder a recursos protegidos.
4. Renovar su sesión utilizando el Refresh Token.
5. Continuar utilizando la aplicación sin volver a ingresar sus credenciales mientras el Refresh Token sea válido.
