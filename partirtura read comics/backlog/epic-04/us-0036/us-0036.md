# US-0036 — Administrar listas personales de obras

## Historia de usuario

Como usuario autenticado de Comic Library, quiero crear y administrar mis propias listas de obras para organizar mi lectura según mis intereses y criterios personales.

## Objetivo

Permitir que cada usuario cree listas personales, agregue o quite obras, defina su orden de lectura y administre su contenido, reutilizando las funcionalidades existentes de consulta de listas, lectura, progreso, valoraciones y comentarios.

Las listas personales deben integrarse con la experiencia actual de listas del sistema, sin duplicar su implementación.

## Funcionalidades

### 1. Consultar mis listas

- Incorporar una sección **Mis listas** en `/lists`, separada de las listas del sistema.
- Mostrar las listas personales del usuario autenticado.
- Utilizar la misma presentación y comportamiento visual de las tarjetas de listas del sistema.
- Mostrar las obras que pertenecen a cada lista mediante los mecanismos existentes.
- Utilizar una portada genérica para las listas personales, ya que no poseen una portada propia.
- Permitir acceder al detalle de cada lista.

### 2. Crear una lista

- Permitir crear una lista personal indicando únicamente su nombre.
- No solicitar portada, descripción, color ni tipo de lista.
- Asociar automáticamente la lista al usuario autenticado.
- Una lista recién creada puede no contener obras.

### 3. Modificar una lista

- Permitir cambiar el nombre de una lista personal.
- No permitir modificar listas pertenecientes al sistema mediante las operaciones de administración personal.

### 4. Eliminar una lista

- Permitir eliminar físicamente una lista personal propia.
- La eliminación debe quitar también todos los registros que relacionan obras con esa lista.
- Eliminar una lista no debe eliminar las obras del catálogo ni afectar otras listas, el progreso de lectura, las valoraciones, los comentarios o los favoritos.
- Solicitar confirmación antes de completar la eliminación.

### 5. Agregar y quitar obras desde las tarjetas

- Incorporar en las tarjetas de obras un botón para administrar su pertenencia a listas personales.
- El botón debe abrir un modal que muestre las listas personales del usuario autenticado.
- Cada lista debe disponer de una casilla que indique si la obra pertenece a ella.
- El estado inicial de cada casilla debe reflejar la información persistida.
- Permitir agregar la obra a una lista o quitarla de ella desde el modal.
- Reflejar visualmente el estado de pertenencia en el botón:
  - Gris cuando la obra no pertenece a ninguna lista personal.
  - Azul, verde o amarillo cuando pertenece a una o más listas personales, siguiendo las convenciones visuales existentes en el proyecto.
- Actualizar el estado visual después de confirmar correctamente cada operación, sin representar como persistido un cambio que haya fallado.

### 6. Consultar y administrar el detalle

- Mostrar el detalle de una lista personal con la misma estructura y experiencia de las listas del sistema.
- Mostrar sus obras utilizando los componentes existentes.
- Permitir reordenar las obras mediante drag & drop.
- Persistir el nuevo orden en el backend.
- Permitir quitar una obra de la lista desde su detalle.
- Quitar únicamente la relación entre la lista y la obra, sin eliminar la obra del catálogo ni sus datos asociados.

### 7. Reutilizar la experiencia de lectura

Las obras de una lista personal deben conservar las funcionalidades existentes de las listas del sistema:

- Abrir una obra para leerla.
- Consultar y actualizar el progreso de lectura.
- Valorar las obras.
- Consultar y publicar comentarios cuando la funcionalidad existente lo permita.

No se deben implementar versiones alternativas de estas funcionalidades para las listas personales.

## Reglas de negocio

- Todas las operaciones requieren autenticación.
- Cada usuario solo puede consultar y administrar sus propias listas personales.
- No se debe permitir consultar, modificar, reordenar o eliminar listas personales de otro usuario mediante la manipulación de identificadores.
- Las listas personales y las listas del sistema deben conservar su identidad y reglas de administración diferenciadas.
- Las listas del sistema continúan funcionando como hasta ahora.
- Las operaciones sobre listas personales no deben modificar la pertenencia de las obras a listas del sistema.
- El orden de las obras debe mantenerse después de recargar la página o volver a abrir la lista.
- La eliminación de una obra de una lista no debe confundirse con la eliminación de la obra del catálogo.

## Criterios de aceptación

1. El usuario puede consultar sus listas personales desde `/lists`, en una sección separada de las listas del sistema.
2. Las listas personales utilizan la presentación existente de las tarjetas de listas y una portada genérica.
3. El usuario puede crear una lista indicando únicamente su nombre.
4. El usuario puede modificar el nombre de una lista propia.
5. El usuario puede eliminar una lista propia y todos sus registros de pertenencia, sin eliminar las obras ni afectar otras funcionalidades.
6. Las tarjetas de obras permiten abrir un modal con las listas personales del usuario.
7. El modal muestra correctamente qué listas contienen la obra y permite agregarla o quitarla de cada una.
8. El botón de administración de listas refleja si la obra pertenece a alguna lista personal.
9. El detalle de una lista personal reutiliza la presentación y las funcionalidades existentes de las listas del sistema.
10. El usuario puede reordenar las obras mediante drag & drop y el orden persiste en el backend.
11. El usuario puede quitar obras de una lista sin eliminar las obras del catálogo.
12. La lectura, el progreso, las valoraciones y los comentarios continúan funcionando sin duplicar su implementación.
13. Un usuario no puede administrar listas personales pertenecientes a otro usuario.
14. Las listas del sistema conservan su comportamiento actual y no pueden modificarse mediante las operaciones de listas personales.
15. La experiencia es responsive y mantiene las convenciones visuales del proyecto.
16. Los estados de carga, error, vacío y confirmación se integran con los mecanismos existentes.

## Fuera de alcance

- Compartir listas personales con otros usuarios.
- Crear listas colaborativas o comunitarias.
- Agregar portadas, descripciones, colores o tipos configurables a las listas personales.
- Implementar nuevas funcionalidades de lectura, progreso, valoraciones o comentarios.
- Modificar las reglas de administración de las listas del sistema.
- Implementar recomendaciones o generación automática de listas mediante inteligencia artificial.
- Corregir aspectos generales del catálogo que no sean necesarios para esta historia: retirar elementos que no deban mostrarse, incorporar el promedio de valoraciones a todas las tarjetas de obras y realizar ajustes estéticos generales. Estos puntos quedan reservados para una pasada posterior.

## Consideraciones de implementación

- Antes de crear componentes o contratos nuevos, revisar la implementación existente de listas del sistema, tarjetas de listas, detalle, tarjetas de obras y sus respectivos contratos de API.
- Reutilizar los componentes y servicios existentes cuando corresponda, incorporando el contexto personal sin duplicar páginas ni lógica.
- Definir los contratos de API y las decisiones técnicas en los artefactos correspondientes del proyecto.
- Mantener la separación entre la definición funcional de esta historia y las decisiones de arquitectura e implementación.
